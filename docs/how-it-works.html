Ad Ops Command Center · Phase 1

An AI that writes ad reports — and a second AI that checks every number in them.

Language models make up plausible-sounding figures. This pipeline catches them: every claim in a generated report is checked against the real data, and anything unsupported is sent back to be rewritten.

Plain-English explainer first. Architecture, method and limitations from “Under the hood” down.

How it works

01 The data DuckDB

Real ad performance numbers, queried into a fixed, structured record. This is the only source of truth.

02 The writer Claude

Reads those numbers and writes two summaries — one for analysts, one in plain English.

03 The checker Claude

Pulls out every factual claim in the write-up and marks it supported or not — against the data, not its own memory.

04 The report Verified

Published only once every claim holds up against the numbers.

03 ──▶ 02

If anything fails, the flagged claims go back to the writer with the real values attached — fix exactly these, leave the rest alone. Capped at two rewrites, so it can never loop forever.

What the checker actually does

A real run. The writer was handed a draft with errors planted in it; here is what came back.

First draft — 5 of 7 claims unsupported

PASS “delivered 217,715 impressions”
FAIL “achieved an overall CTR of 55%” Actual CTR is 36.9%, not 55%.
FAIL “on $4,200 spend” Total spend is $67.42, not $4,200.
FAIL “impressions rose 30% week-over-week” Impressions fell 7.06%. Wrong direction.
FAIL “the strongest fortnight of the quarter” No quarterly data exists to support this.

After one rewrite — 7 of 7 pass

PASS “achieved an overall CTR of 36.9%” Corrected to the real figure.
PASS “impressions fell 7.06%” Direction corrected.
PASS — the quarterly claim is gone — Removed rather than invented. It couldn't be supported, so it was dropped.

What's being analysed

Real advertising data — 500,000 ad impressions from the Criteo attribution dataset, covering 31 days.

Plus click-through rate, spend, and week-over-week change — the everyday numbers an ad operations team reports on.

The result

100%→0%

Reports written without the real numbers contained a false claim every single time. Reports written with them: never. Measured across 33 different date ranges — 66 runs, no cherry-picking.

Why this is different

  • 01It measures itself. Most AI demos claim to reduce hallucination. This one puts a number on it, and publishes every run behind that number.
  • 02The fix is specific, not vague. The writer isn't told “try again” — it's handed the exact claims that failed, with the correct values, and told to change only those.
  • 03It's a workflow, not an agent. The steps are fixed in code; the AI only writes and checks. That constraint is deliberate — a predictable path is what makes the result measurable in the first place.
  • 04Honest about its limits. 0% means the checker found nothing wrong across 33 runs — not that hallucination is now impossible.

Under the hood

How it's built, and why those choices

The implementation detail behind the summary above — the pattern, the experimental design, and what the result does and doesn't establish.

The contract between stages

Every stage hands off a typed object, not free text. The model's output is constrained to a schema at the API level (messages.parse with a Pydantic model), so there is no regex parsing and no “the model returned prose this time” failure mode. 

# 1. Ground truth — computed in SQL, never by the model
class MetricsSummary:
    start_date, end_date: str
    total_impressions, total_clicks, total_conversions: int
    overall_ctr, total_spend: float
    days: list[DailyMetric]          # per-day breakdown
    week_over_week: list[WeekOverWeek]

# 2. What the writer must produce
class GeneratedReport:
    technical_summary: str
    plain_summary: str

# 3. What the checker must produce — one verdict per claim
class ClaimCheck:
    claim: str          # quoted verbatim from the summary
    supported: bool
    explanation: str    # if unsupported, the REAL value

class EvaluationResult:
    claims: list[ClaimCheck]
    @property unsupported            # -> list[ClaimCheck]
    @property has_unsupported_claims # -> bool  (drives the loop)

The important detail is explanation carrying the true value. That's what makes the retry corrective rather than a reroll — the writer receives the right answer, not just a rejection.

The loop

Termination is structural

The loop is a bounded for range, not a while on model output. Worst case is 3 drafts and 6 API calls; there is no prompt phrasing or model behaviour that can extend it.

Why it matters: an unbounded self-correcting loop is a runaway cost incident waiting to happen.

The retry prompt is narrow

The reviser gets the ground-truth JSON, its own previous draft, and a numbered list of only the failed claims with their real values — plus an instruction to keep everything already correct unchanged.

Observed effect: when a claim can't be supported at all, it gets deleted rather than replaced with a guess.

The experiment

Two arms, one difference. Both run the identical evaluator and the identical correction loop, so the only variable is what the writer was given.

ArmWhat the writer receivesFirst-draft rateClaim-levelAfter loop
Ungrounded Date range + total impressions only 100% 85.8% 0%
Grounded Full metrics object as JSON 0% 0% 0%

Why the ungrounded arm still gets one real number. Handing the model nothing would make 100% true by construction and prove nothing. Giving it the period and the headline volume, then asking for a full report, reproduces the realistic failure case: someone knows the top-line figure and asks a model to fill in the rest. Every remaining figure — CTR, spend, conversions, week-over-week direction — has to be invented.

Three rates, because they answer different questions. First-draft is the share of reports with at least one bad claim. Claim-level is the share of individual claims that were wrong, which measures severity rather than mere presence. After loop is what survived the pipeline.

33 date ranges × 2 arms = 66 runs, spanning 14-, 21- and 28-day windows so the result isn't an artefact of one window size. Zero runs errored. Both arms use claude-opus-4-8.

The obvious objection

“You're using Claude to check Claude. Isn't that circular?”

It's the right question, and it's a real limitation — but the two tasks aren't symmetric. The writer performs generation: it must produce figures. The checker performs extraction and comparison: the ground truth is in its context window, and its job is to pull out each claim and compare it against a number that's sitting right there. That's a substantially easier task, and a different failure mode.

It's also verifiable rather than taken on faith. Feed the checker a draft with known planted errors and confirm it flags exactly those — that's the --demo path, and it's the run shown further up this page.

What it does not rule out: a claim both models are wrong about in the same direction. A deterministic assertion layer for numeric claims — parse the figure, compare to the metrics object in Python, no model involved — would close that gap and is the natural next hardening step.

Engineering notes

The sweep is resumable

Results are written after every run and completed runs are skipped on re-invocation. An interrupted sweep loses at most the single run in flight, and re-running a finished sweep makes zero API calls.

This was not hypothetical — a run was killed at 37 of 66 and resumed without repeating paid work.

Writes are atomic

Saving after every run means a plain truncating write could be interrupted mid-write and destroy all 66 results. Results are written to a temp file and renamed, so the file is always either the complete old version or the complete new one.

Failures are isolated

A run that raises records an error row and the sweep continues, rather than losing the whole batch to one transient API error. Errored runs are retried on resume; successful ones never are.

Cheap to reproduce

The full 66-run sweep costs roughly $4 and about 25 minutes. Every run is committed as JSON, so the headline number can be reprinted for free without touching the API.

What this doesn't establish

  • 010% is a ceiling, not a proof. It means the checker found nothing unsupported in 33 runs on this dataset — not that grounding makes hallucination impossible.
  • 02One dataset, one domain. Criteo attribution data, one metric schema. The pattern should generalise; the number is not claimed to.
  • 03Both arms share a model. The rates describe claude-opus-4-8. A weaker writer would likely hallucinate even when grounded.
  • 04The checker is the instrument. It is deliberately not run on a cheaper model — that would reduce the claim to “as judged by a cheaper fact-checker.”
